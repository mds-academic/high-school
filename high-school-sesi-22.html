Sulit dibaca

b = x + a

Lebih deskriptif

total_bayar = harga_barang + nilai_pajak

Prompt Refactoring: Buat Batas yang Jelas

Contoh prompt

Saya sedang belajar Python tingkat pemula-menengah.

Saya memiliki kode project CLI yang sudah berjalan lancar dan lulus pengujian.

Tolong berikan saran refactoring dengan ketentuan: jangan mengubah fungsi, logika perhitungan, nama menu, atau expected output; jangan menambahkan library luar, class, lambda, atau sintaks tingkat lanjut; fokus pada penamaan variabel, duplikasi kode, dan indentasi/komentar; jelaskan alasan teknisnya.

Before: Kode Sulit Dibaca

# Nama variabel tidak jelas
x = 100000
a = x * 0.11
b = x + a
print(f"Total: Rp {b}")

Code smell yang terlihat

Nama satu huruf dan angka pajak langsung ditulis di rumus.

After: Clean Code

# Menggunakan Constant & Function Reusable
PERSEN_PAJAK_SIMULASI = 11

def hitung_pajak(harga):
    nilai_pajak = harga * (PERSEN_PAJAK_SIMULASI / 100)
    return harga + nilai_pajak

harga_barang = 100000
total_bayar = hitung_pajak(harga_barang)
print(f"Total: Rp {total_bayar:,.0f}")

Output

Sebelum: Total: Rp 111000.0 · Sesudah: Total: Rp 111.000

Materi menyatakan fungsi dan hasil utama tidak berubah.

Dari “benar” menjadi “rapi”

Pada Sesi 21, kamu membuktikan bahwa rumus dan output project benar. Sekarang pertanyaannya berubah: apakah orang lain bisa membaca kode tersebut tanpa harus menebak arti variabel atau mencari blok yang berulang?

Sesi 22 menggunakan AI sebagai co-pilot reviewer. AI boleh memberi alternatif struktur, tetapi keputusan akhir tetap di tangan kamu. Materi menekankan bahwa refactoring bukan alasan untuk menambah fitur baru atau mengganti alur menu.

Jadi baseline-mu adalah kode yang sudah lulus pengujian Sesi 21. Setelah dirapikan, baseline itu harus tetap menjadi patokan.

Kenapa urutannya begitu?

Kalau project belum terbukti bekerja, kamu belum punya baseline yang kuat untuk membedakan “kode sudah dirapikan” dari “kode baru jadi berbeda”. Sesi 22 sengaja datang setelah audit akurasi Sesi 21.

Dengan project yang sudah lulus pengujian, kamu bisa membandingkan perilaku sebelum dan sesudah perubahan. Itu yang nanti disebut Regression Testing.

Cara kerja ini juga mengurangi risiko: perubahan dilakukan bertahap, bukan seluruh codebase langsung dirombak.

Yang berubah adalah bagian dalam

Kamu boleh mengganti nama variabel, memindahkan kode berulang ke function reusable, atau merapikan indentasi dan komentar. Yang tidak boleh berubah adalah fungsi utama program dan expected output yang sudah disepakati.

Bayangkan program sebagai alat. Refactoring memperbaiki susunan komponen di dalam alat, tetapi tombol yang ditekan user dan hasil yang keluar tetap sama.

Karena itu, refactoring membutuhkan disiplin: setiap perubahan harus bisa dijelaskan dan diuji.

Lihat apa yang berubah

Kalau hanya struktur internal yang berubah dan perilaku program tetap sama, itu refactoring. Kalau kamu memperbaiki perhitungan yang salah, itu debugging. Kalau kamu menambah kemampuan yang sebelumnya belum ada, itu penambahan fitur.

Materi sesi 22 secara khusus meminta agar alur menu yang sudah disetujui pada Sesi 16–21 tidak diubah. Fokus sesi adalah code quality, bukan memperbesar scope project.

Batas ini penting supaya hasil refactoring mudah diverifikasi. Semakin banyak hal yang berubah sekaligus, semakin sulit menentukan sumber perubahan output.

Nama variabel adalah petunjuk

Variabel satu huruf tidak selalu salah, tetapi pada project yang mulai lebih panjang, nama seperti x, a, atau temp membuat pembaca harus membuka lebih banyak baris untuk memahami artinya.

Nama seperti harga_barang dan total_bayar sudah memberi konteks tanpa harus membaca rumus terlebih dahulu. Materi sesi 22 menyebut penamaan yang tidak jelas sebagai salah satu indikator code smell.

Saat memilih nama baru, jangan hanya pilih nama yang panjang. Pilih nama yang menggambarkan peran datanya dengan jelas dan tetap mudah dipahami oleh kamu sendiri.

Kenapa duplikasi jadi masalah?

Kalau teks header harus diubah dan salinan yang sama muncul di tiga tempat, kamu harus mengubah tiga bagian. Satu tempat yang tertinggal bisa membuat output tidak konsisten.

Refactoring dapat memindahkan blok yang sama ke function reusable. Setelah itu, bagian lain cukup memanggil function tersebut. Struktur lebih pendek dan perubahan menjadi lebih terpusat.

Yang perlu dijaga adalah perilakunya. Kalau header sebelumnya muncul pada tiga tempat, pastikan refactoring tetap menghasilkan header pada tiga tempat yang sama.

Function yang terlalu panjang

Materi sesi 22 memasukkan function terlalu panjang sebagai code smell karena satu fungsi dapat memegang terlalu banyak tanggung jawab. Saat membaca atau memperbaiki satu bagian, kita harus melewati banyak logika lain.

Refactoring bisa berarti menyederhanakan struktur function atau memindahkan tugas yang memang sudah jelas menjadi helper function. Bukan berarti semua baris harus dipecah menjadi puluhan function.

Gunakan prinsip sederhana: setelah dirapikan, kamu seharusnya lebih mudah menjawab “function ini sebenarnya melakukan apa?”

Nama membantu pembaca memahami konteks

Angka 0.11 tidak langsung menjelaskan arti. Pembaca harus menebak apakah itu pajak, diskon, atau angka lain. Constant seperti PERSEN_PAJAK_SIMULASI memberi konteks.

Perhatikan juga bentuk perhitungannya. Materi sesi 22 menggunakan constant bernilai 11 lalu melakukan / 100 saat menghitung. Ini lebih mudah dibaca sebagai persentase.

Magic number adalah kandidat refactoring selama perubahan tersebut tidak mengubah nilai dan perilaku program.

Kenapa prompt juga punya aturan keamanan?

Materi sesi 22 secara eksplisit melarang memasukkan kata sandi, NIK, nomor rekening asli, atau kunci API ke prompt. Untuk contoh finansial, gunakan angka dan identitas simulasi.

Kamu bisa tetap meminta AI memberi saran refactoring tanpa mengirim informasi yang sensitif. Yang dibutuhkan reviewer adalah struktur program, nama variabel, function, dan bagian kode yang ingin dirapikan.

Sebelum menekan send, baca kembali potongan kode seperti kamu sedang memeriksa barang yang akan dibagikan ke pihak lain: apakah ada sesuatu yang seharusnya tetap rahasia?

Kenapa dimulai dari satu bagian?

Sesi 22 meminta proses bertahap. Pilih satu function atau satu bagian main menu terlebih dahulu. Setelah perubahan itu terbukti aman, baru lanjut ke bagian berikutnya.

Backup penting supaya kamu punya versi sebelum refactoring. Bila perubahan membuat alur tidak sesuai, kamu masih memiliki baseline yang dapat dibandingkan.

Alur ini juga membuat kerja dengan AI lebih terkontrol. AI memberi saran, kamu mengevaluasi, kamu menerapkan, lalu kamu menguji.

Kenapa prompt harus membatasi AI?

Prompt yang terlalu umum seperti “buat kode saya lebih bagus” memberi ruang perubahan yang terlalu besar. Materi sesi 22 memberi batas yang jauh lebih spesifik agar AI tetap berada di level Python yang sudah dipelajari.

Empat batas penting adalah: fungsi tidak berubah, output tidak berubah, sintaks baru harus dipahami, dan fokus hanya pada clean code. Dengan batas ini, kamu dapat menilai apakah saran AI masih sesuai tujuan sesi.

Anggap prompt sebagai brief untuk code reviewer. Semakin jelas apa yang boleh dan tidak boleh berubah, semakin mudah kamu menilai hasilnya.

Audit sebelum menyentuh kode

Di contoh materi, perilaku kode sebenarnya sederhana: harga awal 100000, pajak 11%, lalu total dicetak. Masalahnya adalah pembaca harus menebak arti x, a, dan b.

Angka 0.11 juga langsung muncul di rumus. Bila angka ini perlu diubah atau dipakai di bagian lain, konteksnya tidak terlihat dari nama apa pun.

Inilah contoh yang cocok untuk refactoring karena struktur dapat diperjelas tanpa mengubah hasil utama.

Apa yang menjadi lebih jelas?

Constant PERSEN_PAJAK_SIMULASI menjelaskan arti angka 11. Function hitung_pajak() membuat logika pajak punya tempat yang jelas. Nama harga_barang dan total_bayar memperjelas peran masing-masing nilai.

Materi juga menekankan penamaan snake_case dan penggunaan function reusable. Struktur baru lebih mudah dipakai kembali tanpa membuat pembaca kehilangan konteks.

Perhatikan bahwa contoh output sesudah refactoring ditampilkan lebih rapi. Saat melakukan regression testing pada project asli, kamu tetap harus memakai expected output yang disepakati project dan memastikan perubahan tampilan tersebut memang tidak mengubah perilaku yang diuji.

Gunakan “perilaku program” sebagai patokan

Refactoring menjaga perilaku. Kalau input tertentu menghasilkan output tertentu sebelum dirapikan, hasil itu harus tetap konsisten setelah perubahan, kecuali kamu memang sedang melakukan debugging dan menyatakan perubahan logika tersebut secara terpisah.

Itulah sebabnya pengubahan operator yang mengubah hasil perhitungan tidak boleh diberi label refactoring. Begitu juga menambah menu baru, karena kemampuan program bertambah.

Sebelum menerima saran AI, tanyakan satu hal sederhana: “Apakah saran ini mengubah apa yang bisa dilakukan program atau hasil yang keluar?”

Uji dengan definisinya, bukan dengan tampilannya

Mengubah nama variabel dan memindahkan kode berulang adalah perubahan struktur. Karena perilaku program tetap dapat dipertahankan, keduanya masuk refactoring.

Menambah ekspor PDF adalah kemampuan baru, jadi itu penambahan fitur. Mengubah rumus potongan mengubah logika output, jadi bukan refactoring.

Latihan ini penting karena saat menerima saran AI, perubahan sering terlihat “lebih rapi” padahal sebenarnya mengubah perilaku. Label yang benar berasal dari dampaknya pada program.

Kenapa saran AI perlu dinilai?

Materi sesi 22 meminta kamu menolak sintaks yang belum dipelajari, termasuk class, lambda, atau library asing. Kode yang “lebih singkat” belum tentu lebih cocok untuk project belajar.

Kamu adalah orang yang paling tahu tujuan project, aturan menu, expected output, dan batas materi yang sudah dikuasai. AI dapat membantu melihat alternatif, tetapi keputusan penerapan tetap harus berdasarkan auditmu.

Ini juga bagian penting dari pembelajaran: kamu tidak hanya meminta kode, tetapi belajar menjelaskan alasan teknis di balik keputusan untuk menerima atau menolak sebuah perubahan.

Empat pertanyaan sebelum menerima saran

Pertama, cek kesesuaian fitur: apakah keluaran tetap persis sesuai baseline? Kedua, cek pemahaman sintaks: apakah kamu mengerti setiap baris yang berubah?

Ketiga, cek keamanan logika: jangan sampai try-except atau kondisi seperti if not data: terhapus hanya karena AI ingin mempersingkat kode. Keempat, cek keterbacaan: nama baru harus benar-benar lebih jelas, bukan sekadar lebih panjang.

Checklist ini membantu kamu mengubah proses “AI memberi kode” menjadi “AI memberi saran yang diaudit”.

Kenapa regression testing berbeda dengan testing awal?

Sebelum refactoring, kamu menguji apakah project bekerja. Setelah refactoring, kamu menguji apakah perubahan struktur merusak sesuatu yang sebelumnya sudah bekerja.

Karena itu test case sebaiknya memakai input yang sama seperti baseline. Dengan pasangan output sebelum/sesudah, kamu punya pembanding yang jelas.

Kalau satu test berubah menjadi FAIL, jangan langsung meneruskan refactoring. Cari perubahan yang memengaruhi hasil, perbaiki, lalu jalankan test lagi.

Yang dicari adalah konsistensi perilaku

Tabel regression test dari materi membandingkan input uji dan output sebelum/ sesudah refactoring. Bila keduanya konsisten, test dinyatakan PASS.

Contoh mencakup function hitung, main menu loop, dan error handling. Jadi regression testing tidak hanya memeriksa function yang dirapikan; bagian lain yang berhubungan dengan perubahan juga perlu dipastikan tetap berjalan.

Gunakan test yang sudah pernah kamu jalankan sebagai baseline. Ini mengurangi pekerjaan dan membuat perbandingan lebih terpercaya.

Mulai dari perubahan terkecil

Mengganti satu nama variabel adalah contoh perubahan kecil yang mudah diperiksa. Kamu bisa langsung mencari semua pemakaian x lalu menggantinya secara konsisten dengan nama yang lebih deskriptif.

Setelah itu, jalankan test case yang sebelumnya PASS. Bila output sama, kamu punya satu perubahan refactoring yang sudah tervalidasi.

Pendekatan bertahap seperti ini juga membuat debugging lebih mudah bila ada kesalahan ketik atau referensi variabel yang tertinggal.

Apa yang sebenarnya dirapikan?

Blok cetak yang sama dipindahkan ke satu function reusable. Dua titik pemanggilan masih ada, sehingga perilaku program dapat dipertahankan.

Perubahan ini bukan penambahan fitur. Header sudah ada sebelumnya. Refactoring hanya mengubah cara kode disusun agar duplikasi berkurang dan perubahan berikutnya menjadi lebih mudah.

Saat menguji, pastikan header masih muncul pada lokasi yang sama. Jangan hanya melihat bahwa function baru “berjalan”; cek seluruh alur yang terdampak.

Clean Code tidak berarti “hapus semua yang terlihat panjang”

Error handling yang sudah dipasang pada sesi sebelumnya punya fungsi. Kalau AI menghapus try-except hanya agar function terlihat lebih pendek, struktur memang menjadi singkat tetapi perilaku program berubah.

Hal yang sama berlaku pada kondisi pengaman data kosong. Jika program sebelumnya menangani kondisi kosong dengan aman, refactoring harus mempertahankan perilaku tersebut.

Jadi evaluasi AI bukan hanya “apakah kode lebih pendek?”, melainkan “apakah kode tetap benar dan lebih mudah dipahami?”

Kenapa keputusan perlu didokumentasikan?

Log membuat proses refactoring bisa ditelusuri. Guru dan kamu sendiri dapat melihat bagian mana yang berubah dan mengapa.

Saran yang ditolak juga penting. Menolak sintaks class karena belum dipelajari adalah keputusan yang sah dalam konteks pembelajaran, terutama ketika function yang ada sudah cukup modular untuk project.

Tuliskan alasan yang spesifik: lebih mudah dibaca, mengurangi duplikasi, mempertahankan logika, atau masih di luar materi yang sudah dipelajari.

Kamu tidak perlu menguasai semua teknik software engineering sekaligus. Fokus sesi ini adalah kebiasaan dasar yang dapat langsung dipakai pada project Python CLI yang sedang kamu bangun.

Refactoring meningkatkan keterbacaan dan kualitas struktur kode tanpa mengubah hasil keluaran eksternal program. Clean Code pada sesi ini menekankan nama variabel yang deskriptif, pengurangan kode berulang, dan kejelasan function.

AI berperan sebagai co-pilot reviewer. Ia memberikan alternatif, tetapi kamu memegang kendali atas penerapan. Keamanan data tetap dijaga dengan data simulasi.

Setelah perubahan diterapkan, Regression Testing wajib dilakukan untuk memastikan fitur dan logika yang sebelumnya benar tetap berjalan. Baseline dari Sesi 21 menjadi pembanding utama.
