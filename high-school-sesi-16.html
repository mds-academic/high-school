Apa Itu Pseudocode?

Pseudocode vs Flowchart

Keduanya membantu merancang alur, tapi bentuknya berbeda.

STARTMulai program

Flowchart = visual. Pseudocode = tulisan langkah-langkah.

Struktur Pseudocode yang Rapi

Pseudocode yang bagus biasanya punya urutan: mulai, input, proses, keputusan, output, selesai.

START tampilkan judul aplikasi minta nama user minta pemasukan minta total kebutuhan minta total keinginan hitung total_pengeluaran hitung sisa_uang IF sisa_uang >= 0 THEN tampilkan status aman ELSE tampilkan status perlu evaluasi ENDIF END

Perhatikan indentasi

Langkah di dalam IF dibuat menjorok supaya kelihatan bahwa bagian itu hanya berjalan saat kondisi tertentu.

Kenapa Sesi Ini Penting?

Mulai sesi ini, kamu masuk fase project. Artinya, kamu tidak hanya mengikuti contoh kode, tapi mulai mengambil keputusan: aplikasi apa yang mau dibuat, masalah apa yang ingin dibantu, dan bagaimana alur programnya.

Pseudocode membantu kamu menata ide sebelum coding. Pitch deck membantu kamu menjelaskan ide itu ke orang lain. Dua-duanya penting karena project yang bagus bukan hanya “kodenya jalan”, tapi juga punya tujuan yang jelas.

Prinsip sesi ini

Jangan buru-buru membuat fitur banyak. Buat dulu pondasi yang jelas: masalah, fitur utama, pseudocode, prototype awal, dan rencana demo.

Alur Kerja Sesi

Hari ini alurnya dimulai dari ide, bukan dari kode. Kamu akan memilih masalah sederhana, mengubahnya menjadi input-proses-output, lalu menulis pseudocode. Setelah itu baru dibuat prototype CLI versi awal.

Di akhir sesi, kamu juga menyiapkan pitch deck. Pitch deck ini belum harus sempurna. Fungsinya sebagai wadah awal untuk menjelaskan project: siapa usernya, masalahnya apa, solusi aplikasinya apa, dan fitur apa yang akan ditunjukkan.

CLI dengan Pola Input-Process-Output

CLI atau command-line interface adalah aplikasi yang digunakan lewat teks. Di Python, interaksi paling dasarnya memakai input() untuk menerima data dan print() untuk menampilkan hasil.

Agar ide project tidak berantakan, pikirkan semua fitur dengan pola IPO: input apa yang diminta, proses apa yang dilakukan program, dan output apa yang dilihat user. Kalau tiga bagian ini belum jelas, biasanya kode akan mudah melebar ke mana-mana.

Contoh cepat

Input: pemasukan dan pengeluaran. Process: hitung sisa uang. Output: status budget dan saran singkat.

Arah Project Financial Helper

Contoh project pada sesi ini memakai tema financial helper karena cocok untuk latihan Python dasar: ada input angka, perhitungan, kondisi, output teks, dan pesan rekomendasi sederhana.

Project ini tidak perlu menjadi aplikasi bank atau aplikasi keuangan profesional. Cukup bantu user memahami data sederhana. Misalnya, “apakah budget bulan ini masih aman?” atau “berapa sisa uang yang mungkin bisa ditabung?”

Batasan penting

Program tidak memberi nasihat finansial personal yang serius. Program hanya memberi saran edukatif berdasarkan data dummy atau data latihan.

Memilih Masalah yang Pas

Masalah project yang baik untuk sesi ini harus cukup spesifik. Kalau masalahnya terlalu besar, seperti “mengatasi semua masalah keuangan”, fitur yang dibutuhkan akan terlalu banyak. Mulailah dari satu kebiasaan atau satu keputusan kecil.

Contoh yang pas: siswa ingin mengecek sisa uang jajan, ingin tahu target tabungan per bulan, atau ingin mempertimbangkan apakah sebuah pembelian perlu ditunda. Masalah seperti ini bisa dibuat dengan input, perhitungan, dan kondisi sederhana.

Scope Fitur Utama

Untuk sesi 16, fitur utama tidak perlu banyak. Justru lebih baik satu fitur yang jelas dan selesai. Nanti pada sesi 17 dan 18, project akan dikembangkan dengan main menu loop dan function.

Kalau kamu memilih fitur cek budget, jangan langsung menambahkan grafik, login, database, dan export file. Mulai dari flow sederhana: minta data, hitung, tampilkan status. Kalau pondasi ini kuat, fitur tambahan akan lebih mudah dibuat.

Kalimat uji scope

Kalau kamu bisa menjelaskan fitur dalam satu kalimat input-proses-output, berarti fiturnya cukup jelas untuk mulai dibuat.

Pseudocode Membantu Otak Kita

Pseudocode bukan kode yang dijalankan komputer. Pseudocode adalah jembatan antara ide dan kode. Dengan pseudocode, kamu bisa mengecek apakah urutan berpikirmu sudah masuk akal sebelum terjebak di syntax Python.

Pseudocode boleh memakai Bahasa Indonesia. Yang penting langkahnya jelas, runtut, dan bisa diterjemahkan ke Python. Biasanya pseudocode yang rapi membuat proses coding jauh lebih cepat.

Kesalahan umum

Jangan menulis pseudocode terlalu abstrak seperti “buat aplikasi keren”. Tulis langkah yang benar-benar bisa dilakukan program.

Flowchart dan Pseudocode

Flowchart membantu kamu melihat alur secara visual. Pseudocode membantu kamu menulis langkah dengan lebih detail. Keduanya boleh dipakai bersamaan.

Untuk project CLI, flowchart berguna saat menjelaskan alur di pitch deck. Pseudocode berguna saat mulai coding di notebook. Kalau project mulai memakai menu dan loop pada sesi 17, flowchart juga akan membantu melihat kapan program kembali ke menu utama.

Urutan Pseudocode

Pseudocode yang rapi punya urutan logis. Mulai dari judul aplikasi, lalu input, proses perhitungan, keputusan, output, dan selesai. Untuk percabangan, gunakan IF, ELSE, dan ENDIF agar batas kondisinya jelas.

Indentasi di pseudocode tidak wajib seperti Python, tapi sangat membantu. Bagian yang menjorok menunjukkan bahwa langkah itu hanya terjadi di dalam kondisi tertentu.

Tips

Sebelum coding, baca pseudocode dari atas ke bawah. Kalau masih ada langkah yang terasa loncat, rapikan dulu.

Bagian-Bagian Pseudocode

Setiap bagian punya fungsi. START/END memberi batas alur. INPUT menjelaskan data yang diminta. PROCESS menjelaskan perhitungan atau pengolahan. IF menjelaskan keputusan. OUTPUT menjelaskan informasi yang ditampilkan.

Kalau pseudocode kamu hanya berisi input dan output tanpa proses, mungkin aplikasinya belum benar-benar membantu. Kalau ada proses tapi tidak ada output, user tidak akan tahu hasilnya.

Menerjemahkan ke Python

Proses coding menjadi lebih ringan kalau kamu menerjemahkan pseudocode satu baris demi satu baris. “Minta nama user” bisa menjadi nama = input(...). “Hitung sisa uang” bisa menjadi operasi matematika. “Jika sisa aman” bisa menjadi if.

Jangan langsung mengejar kode panjang. Buat beberapa baris dulu, jalankan, cek output, lalu lanjut. Cara ini mengurangi bug besar yang sulit dilacak.

Prototype CLI Versi Awal

Prototype ini menunjukkan alur dasar project: program menampilkan judul, meminta input, menghitung pengeluaran dan sisa uang, lalu memberi status. Ini belum aplikasi final, tapi sudah cukup untuk membuktikan ide awal.

Perhatikan penggunaan int(input(...)). Input dari user awalnya berbentuk teks, lalu diubah menjadi angka agar bisa dihitung. Perhatikan juga f-string untuk membuat output lebih rapi dan mudah dibaca.

Hal yang belum sempurna

Kalau user mengetik huruf pada input angka, program bisa error. Itu bukan gagal total; catat sebagai bagian yang akan diperbaiki saat pengembangan berikutnya.

Trace dan Test Case

Trace membantu kamu melihat perubahan nilai. Misalnya, jika pemasukan 2.500.000, kebutuhan 1.500.000, dan keinginan 500.000, total pengeluaran adalah 2.000.000. Sisa uang adalah 500.000.

Test case membantu membuktikan program tidak hanya bekerja pada satu contoh. Coba case aman, pas-pasan, minus, dan input salah. Untuk sesi 16, kalau input salah masih error, catat sebagai batasan prototype.

Validasi Input sebagai Backlog

Validasi input adalah proses mengecek apakah input user sesuai aturan. Misalnya, pemasukan harus angka, bukan teks. Pada prototype awal, validasi belum harus lengkap.

Namun, developer yang baik tetap mencatat batasan. Kalau program belum bisa menangani input “dua juta”, tulis di notebook: “Saat ini input angka harus memakai digit. Validasi input akan dikembangkan.” Ini membuat proses project terlihat jujur dan rapi.

Decision Membuat Output Lebih Bermakna

Tanpa if/else, program hanya menghitung angka. Dengan decision, program bisa memberi pesan sesuai kondisi. Misalnya, jika sisa uang positif, tampilkan status aman. Jika negatif, tampilkan saran evaluasi.

Decision pada sesi ini masih sederhana. Nanti, saat project memakai menu dan function, decision ini bisa dipindahkan ke function khusus agar kode lebih rapi.

Menyusun Pseudocode Sendiri

Pseudocode builder di slide kiri hanya contoh. Saat mengerjakan notebook, kamu tetap perlu menyesuaikan dengan ide project masing-masing. Jangan takut memakai kalimat sederhana.

Yang penting, pseudocode harus bisa menjadi panduan coding. Kalau kamu membaca pseudocode lalu tahu baris Python apa yang perlu dibuat, berarti pseudocode-nya sudah membantu.

Project Brief sebagai Batas Kerja

Project brief adalah ringkasan pekerjaan yang akan kamu buat. Brief membuat kamu tidak keluar jalur. Jika brief kamu menyebut fitur utama “cek budget”, maka sesi ini fokus membuat alur cek budget dulu.

Brief juga membantu guru membaca arah project. Saat nanti ada revisi, kamu bisa melihat apakah revisinya memperkuat fitur utama atau malah membuat project terlalu melebar.

Notebook yang Mudah Dinilai

Notebook yang rapi menunjukkan proses berpikir. Jangan hanya mengumpulkan code cell tanpa penjelasan. Tambahkan markdown untuk judul, problem statement, pseudocode, test case, dan next step.

Bagian test case penting karena membuktikan kamu tidak hanya menjalankan satu contoh. Bagian next step penting karena project ini akan dilanjutkan pada sesi berikutnya.

Komentar yang Tepat

Komentar sebaiknya menjelaskan alasan, tujuan, atau konteks. Komentar yang hanya mengulang kode biasanya tidak terlalu membantu. Misalnya, # menghitung terlalu umum. Lebih baik jelaskan kenapa perhitungan itu penting.

Dalam project, komentar juga bisa menandai bagian yang akan dikembangkan nanti, misalnya “validasi input akan ditambahkan pada versi berikutnya”.

Testing dari Awal

Testing sebaiknya dimulai sejak prototype masih kecil. Kalau menunggu project besar baru dites, bug akan lebih susah dicari. Satu perubahan kecil, satu kali test.

Untuk aplikasi budget, test case harus mencakup kondisi berbeda: sisa positif, sisa nol, sisa negatif, dan input yang tidak sesuai. Expected output tidak harus panjang, yang penting jelas.

Mini Debug

Bug pada slide ini adalah logic error. Program berjalan, tapi rumusnya terbalik. Ini contoh kenapa kita perlu perhitungan manual. Kalau pemasukan 2.500.000 dan pengeluaran 2.000.000, sisa harusnya positif 500.000, bukan negatif.

Saat menemukan hasil yang aneh, jangan langsung ubah banyak baris. Cek rumus inti terlebih dahulu, lalu jalankan test case sederhana.

Pitch Deck Membuat Ide Mudah Dipahami

Pitch deck bukan sekadar slide cantik. Pitch deck adalah cara menjelaskan nilai project. Orang lain perlu memahami masalah yang kamu pilih, solusi yang kamu buat, dan bukti bahwa prototype mulai bekerja.

Untuk sesi ini, deck masih berupa setup awal. Jangan habiskan waktu terlalu banyak mempercantik tampilan. Fokus pada isi: problem, solution, feature, dan demo plan.

Kerangka Deck Awal

Struktur deck yang sederhana sudah cukup: judul, problem, solution, feature, prototype, dan next step. Setelah prototype berkembang, kamu bisa menambahkan screenshot output, flowchart, atau test result.

Slide “Next Step” penting karena menunjukkan project ini masih dalam proses. Misalnya, sesi 17 akan menambahkan main menu loop, sedangkan sesi 18 akan merapikan kode dengan function.

Membuat Draft Pitch

Draft pitch tidak harus langsung sempurna. Tujuannya adalah memaksa kita menjelaskan ide dengan kalimat yang pendek dan jelas. Kalau kamu belum bisa menulis problem dan solution, mungkin idenya masih perlu dipersempit.

Setelah draft dibuat, cek apakah fiturnya sesuai dengan prototype. Jangan sampai deck menjanjikan fitur yang belum ada bukti kodenya.

Problem Statement yang Spesifik

Problem statement yang terlalu umum sulit dibuktikan. Kalimat “orang-orang susah mengatur uang” benar, tapi terlalu luas. Lebih baik sebut user dan situasi yang lebih jelas.

Problem statement yang spesifik akan memandu fitur. Jika usernya siswa dan masalahnya pembagian uang jajan, maka fitur input-output juga bisa dibuat lebih tepat.

Solution Statement yang Tidak Kosong

Solution statement harus menjelaskan cara aplikasi membantu user. Jangan hanya menulis “solusinya adalah aplikasi saya”. Jelaskan aktivitas yang dibantu dan manfaat yang diterima user.

Template pada slide kiri bisa dipakai untuk draft awal. Setelah project makin jelas, kamu bisa membuat kalimatnya lebih natural untuk presentasi.

Demo Plan Sejak Awal

Demo plan membantu kamu membayangkan bagaimana aplikasi akan ditunjukkan. Ini penting karena project yang bisa didemokan biasanya punya alur user yang lebih jelas.

Untuk sesi ini, demo cukup menunjukkan program dibuka, user memasukkan data dummy, program menghitung, lalu output muncul. Jangan lupa siapkan input yang aman dan hasil yang sudah dites.

Keamanan Digital dalam Project

Karena project bertema finansial, keamanan data harus diperhatikan sejak awal. Gunakan data dummy di notebook, output, dan screenshot deck. Jangan memakai data pribadi atau angka rekening asli.

Kalau ingin membuat contoh yang terlihat realistis, pakai nama samaran dan angka latihan. Yang dinilai adalah logika program dan cara menjelaskan project, bukan data asli.

Checklist Kualitas

Checklist ini membantu memastikan output sesi 16 lengkap. Pseudocode tanpa prototype belum cukup. Prototype tanpa pseudocode juga kurang, karena alur berpikirnya tidak terlihat.

Sebelum submit, jalankan ulang code cell, cek output, dan baca lagi deck awal. Pastikan semua bagian saling nyambung: masalah, fitur, pseudocode, prototype, test case, dan next step.

Refleksi Sesi 16

Exit ticket membantu kamu menyimpulkan ide project dengan singkat. Kalau kamu bisa menjawab masalah, fitur utama, input, proses, dan output, berarti project sudah punya arah.

Jawaban ini juga bisa langsung dipindahkan ke markdown cell atau pitch deck. Jadi, jangan jawab asal; gunakan sebagai draft nyata untuk project kamu.

Rangkuman

Hari ini kamu menyiapkan pondasi project CLI. Pondasi ini akan dipakai lagi pada sesi 17 dan 18. Sesi 17 akan membuat program lebih interaktif dengan main menu loop, sedangkan sesi 18 akan merapikan kode memakai function.

Ingat pola kerja hari ini: masalah → fitur → input-process-output → pseudocode → prototype → test case → pitch deck. Kalau pola ini rapi, project kamu akan lebih mudah dikembangkan.
