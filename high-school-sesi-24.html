Kenapa ditunjukkan?

break membuktikan Main Menu Loop bisa dihentikan sesuai pilihan user, bukan dengan menghentikan runtime secara paksa.

Q&A 1 — “Kenapa Pakai Function?”

Jawaban inti: Function memisahkan logika menjadi bagian yang lebih kecil. Main menu cukup memanggil function, sehingga kode lebih mudah dibaca, diuji, dan diperbaiki.

Bukti terbaik saat menjawab

Tunjukkan satu function dari project-mu dan jelaskan tugasnya.

Q&A 2 — “Bagaimana Program Menangani Input Salah?”

Jawaban inti: Input numerik dibungkus try-except ValueError. Jika user mengetik huruf, exception ditangkap, pesan ditampilkan, dan validation loop meminta input lagi tanpa menghentikan program.

Q&A 3 — “Di Mana Data Disimpan?”

Jawaban inti: Data sementara disimpan dalam List atau Dictionary di memori runtime Google Colab. State diletakkan di luar loop utama agar tidak dibuat ulang setiap kali menu berputar.

Batasannya

Data runtime bukan penyimpanan permanen. CSV/JSON dapat menjadi future improvement.

Kalau Demo Menemukan Bug?

1. Baca error message

Jangan langsung mengubah banyak baris.

2. Cek perubahan terakhir

Function belum didefinisikan? Indentasi? Variable state salah?

3. Gunakan versi stabil / fallback

Jika bug fatal tidak bisa diperbaiki cepat, kembali ke versi terakhir yang sudah lulus test.

Puncak Sprint Project CLI

Sesi 24 adalah penutup rangkaian project yang telah dikembangkan sejak sesi-sesi sebelumnya. Kamu akan menunjukkan hasil karya dan pemahaman teknis di baliknya.

Project tidak harus memiliki semua fitur impian. Yang perlu dibuktikan adalah fitur inti berjalan, output penting akurat, program menangani kesalahan input dasar, dan kamu mampu menjelaskan function, state, serta keputusan teknis yang digunakan.

Gunakan project final yang sudah didokumentasikan di Sesi 23. Hindari perubahan besar menjelang demo.

Demo bukan sekadar “pernah berhasil”

Aplikasi yang siap demo harus bisa dijalankan kembali dalam kondisi runtime bersih. Kalau hanya bekerja karena beberapa cell pernah dijalankan kemarin, demo masih belum reproducible.

Selain itu, demo perlu menunjukkan lebih dari happy path. Audiens harus melihat bahwa program juga dapat menangani kesalahan input sederhana tanpa crash.

Terakhir, kesiapan berarti kamu tahu apa yang sedang terjadi. Jika ditanya mengapa function dipisah atau di mana riwayat disimpan, kamu bisa menunjuk bagian project yang relevan.

Lakukan checklist sebelum giliran presentasi

Jangan menunggu saat layar sudah dibagikan untuk menemukan notebook yang salah atau deck yang belum final. Buka semua artefak lebih dulu dan susun urutan tab sesuai alur demo.

Kalau ada bug fatal setelah Run all, gunakan versi stabil terakhir yang sudah kamu uji. Sesi ini bukan waktu yang ideal untuk refactoring besar atau penambahan fitur baru.

Pastikan tampilan dapat dibaca dari jarak jauh. Demo yang benar tetapi teksnya terlalu kecil tetap sulit dinilai audiens.

Runtime bersih menguji urutan notebook

Google Colab menyimpan variabel dan function di memori runtime. Kalau kamu menjalankan cell tidak berurutan saat mengembangkan project, program bisa terlihat bekerja karena nilai lama masih tersimpan.

Restart Runtime menghapus kondisi tersebut. Run all kemudian menguji apakah notebook benar-benar memiliki urutan yang lengkap dan masuk akal dari awal sampai akhir.

Jika muncul NameError, periksa apakah variabel atau function digunakan sebelum didefinisikan. Jika data awal hilang, cek apakah state memang diinisialisasi di tempat yang tepat.

“Realistis” tidak harus berarti “data asli”

Kamu tetap bisa membuat demo yang mudah dipahami dengan transaksi fiktif seperti makan siang, transportasi, atau alat tulis. Nilainya boleh terlihat realistis tanpa mengacu pada data pribadi siapa pun.

Periksa juga screenshot dan history output. Kadang data sensitif sudah tidak ada di input terbaru, tetapi masih terlihat di output cell lama.

Jika ada, bersihkan output atau ganti dengan data dummy sebelum presentasi.

Satu deck, dua sumber instruksi yang selaras

Notebook latihan menyebut empat bagian besar: judul & nama pengembang, latar belakang/permasalahan, fitur & demo, lalu kesimpulan/next step. Modul final juga memakai empat slide, tetapi merinci isi dengan lebih spesifik.

Supaya tidak ada informasi yang hilang, masukkan judul dan nama pengembang sebagai header Slide 1, lalu lanjutkan dengan masalah dan target user. Slide 2 fokus pada solusi dan dua fitur. Slide 3 menjadi petunjuk/demo terminal. Slide 4 berisi teknologi dan future improvement.

Jangan memenuhi slide dengan kode. Detail kode bisa ditunjukkan saat Q&A jika diperlukan.

Mulai dari “kenapa aplikasi ini ada?”

Slide pertama membantu audiens memahami konteks sebelum melihat fitur. Hindari deskripsi terlalu umum seperti “aplikasi ini berguna untuk keuangan”. Sebutkan masalah yang konkret.

Target user juga penting karena solusi yang baik selalu dibuat untuk kebutuhan tertentu. Project CLI sederhana bisa sangat relevan jika targetnya jelas.

Judul aplikasi dan nama pengembang bisa diletakkan di bagian atas slide yang sama sehingga struktur tetap empat slide.

Fitur harus terhubung ke masalah

Daftar fitur menjadi lebih bermakna ketika audiens tahu fungsi praktisnya. “Tambah pengeluaran” bukan hanya menu input; fitur itu membantu user membangun riwayat transaksi. “Cek budget” membantu user mengetahui kondisi anggaran.

Pilih fitur yang benar-benar berjalan di project-mu. Tidak perlu memaksakan semua contoh SmartBudget jika project-mu menggunakan ide finansial lain.

Saat demo nanti, utamakan fitur yang paling kuat membuktikan solusi.

Slide ini adalah jembatan menuju live demo

Gunakan screenshot atau potongan terminal yang cukup besar untuk menunjukkan pola penggunaan. Jangan memasukkan seluruh riwayat output yang panjang.

Audiens perlu tahu cara berinteraksi dengan menu sebelum kamu berpindah ke Google Colab. Dengan begitu, saat demo berlangsung mereka dapat mengikuti perubahan state dan output dengan lebih mudah.

Jika live demo gagal karena kendala teknis, screenshot yang sudah disiapkan dapat menjadi fallback bukti alur utama, walaupun live demo tetap menjadi target utama.

Pilih konsep yang bisa kamu jelaskan

Modul memberikan empat konsep utama yang sering muncul dalam project CLI semester ini: loop menu, function, state List/Dictionary, dan try-except. Kamu boleh menyebut lebih sedikit jika itu lebih sesuai project-mu, asalkan benar.

Future improvement harus jelas dipisahkan dari fitur yang sudah ada. Misalnya, kalau data saat ini masih hanya di runtime, penyimpanan CSV adalah rencana berikutnya, bukan kemampuan sekarang.

Slide terakhir membantu audiens melihat bahwa kamu memahami batasan project dan arah pengembangannya.

Demo singkat berarti harus memilih bukti

Tiga menit bukan waktu untuk menjelaskan semua detail. Gunakan pitch untuk memberi konteks, lalu live demo untuk membuktikan fitur utama.

Urutan normal case → invalid input → lihat state → keluar dirancang supaya audiens melihat beberapa kompetensi sekaligus: functionality, robustness, state management, dan loop control.

Latih perpindahan tab sebelum presentasi agar waktu tidak habis untuk mencari cell atau slide.

Mulai dengan alur yang paling stabil

Normal case menunjukkan pengalaman utama user. Pilih data dummy yang sudah kamu uji sebelumnya agar hasilnya mudah diprediksi.

Jelaskan secukupnya. Kamu tidak perlu membacakan setiap output. Sebutkan apa yang sedang dibuktikan, misalnya “transaksi tersimpan dan muncul lagi pada menu riwayat”.

Setelah normal case berhasil, barulah sengaja berikan input yang salah untuk menunjukkan robustness.

Error handling harus terlihat bekerja

Notebook Sesi 24 secara khusus melatih try-except ValueError untuk input numerik. Saat demo, masukkan teks seperti seratus pada kolom yang mengharapkan angka.

Program yang robust tidak langsung force close. Ia menangkap kesalahan konversi, memberi pesan yang jelas, lalu meminta input lagi.

Jika project-mu menggunakan helper function validasi, kamu boleh menunjukkannya saat Q&A. Fokus live demo tetap pada behavior yang terlihat oleh user.

Data berpindah antar-menu karena state tetap tersedia

Notebook latihan Sesi 24 meminta siswa menunjukkan penyimpanan data sederhana dengan List atau Dictionary. Dalam project final, ide yang sama dipakai agar transaksi yang ditambahkan pada satu menu masih dapat dibaca pada menu lain.

State ini bersifat sementara. Ia bertahan selama runtime aktif, bukan sebagai penyimpanan permanen. Restart runtime atau menutup sesi dapat menghapus data jika kamu belum menggunakan file I/O.

Saat demo, tambahkan data terlebih dahulu lalu buka menu riwayat. Itu adalah bukti behavior yang lebih kuat daripada hanya menunjuk variabel di kode.

Loop juga perlu punya jalan keluar

Menu CLI biasanya memakai while True agar terus muncul setelah sebuah fitur selesai. Tanpa kondisi keluar yang benar, user bisa terjebak di dalam loop.

Opsi keluar menunjukkan bahwa kamu memahami kontrol alur. Setelah user memilih menu keluar, break menghentikan loop secara bersih.

Pastikan posisi break tidak terlalu awal sehingga menu berhenti setelah satu transaksi saja.

Hubungkan definisi dengan kode sendiri

Jawaban yang kuat bukan hanya “function membuat kode rapi”. Tunjukkan contoh nyata: misalnya tambah_pengeluaran() menangani proses input dan penyimpanan transaksi, sementara main menu hanya memanggil function tersebut.

Ini menunjukkan decomposition: masalah besar dipecah menjadi tugas-tugas kecil yang punya tanggung jawab jelas.

Jika function juga digunakan ulang, sebutkan manfaat reuse. Tetapi jangan mengklaim reuse jika function hanya dipanggil sekali dan manfaat utamanya adalah pemisahan logika.

Bedakan format error dan logic validation

ValueError menangani kasus seperti teks seratus yang tidak bisa dikonversi menjadi angka. Tetapi angka seperti -50000 tetap dapat dikonversi; jika tidak masuk akal bagi aplikasi, kamu membutuhkan validasi logika terpisah.

Kalau project-mu sudah memiliki kedua lapisan ini, jelaskan keduanya. Ini menunjukkan pemahaman lebih dalam tentang robustness.

Gunakan contoh dari project sendiri, bukan jawaban hafalan yang tidak cocok dengan kodemu.

Ini pertanyaan tentang state, scope, dan keterbatasan

Kalau List diinisialisasi ulang di dalam main loop, data sebelumnya bisa hilang setiap kali loop kembali ke awal. Karena itu, state utama biasanya dibuat sebelum loop kemudian dimodifikasi oleh function.

Jelaskan bahwa data hidup selama runtime aktif. Jangan menyebutnya database atau penyimpanan permanen jika project belum memiliki fitur tersebut.

Future improvement yang logis adalah menyimpan data ke file CSV atau JSON sehingga riwayat bisa dimuat lagi pada sesi berikutnya.

Demo Day bukan sesi refactoring besar

Bug kecil masih bisa terjadi. Yang penting adalah cara kamu mendiagnosisnya. Baca pesan error, tentukan cell atau bagian yang terkait, lalu lakukan perbaikan minimal.

Jangan panik lalu menyalin ulang seluruh project. Perubahan besar di saat terakhir justru menambah risiko.

Jika kendalanya koneksi atau runtime, screenshot output utama dapat membantu menjelaskan fitur. Tetapi setelah itu, tetap jelaskan struktur kodenya agar audiens melihat pemahamanmu.

Nilai berasal dari beberapa jenis bukti

Aplikasi yang berjalan adalah bagian penting, tetapi bukan satu-satunya. Struktur kode, ketahanan terhadap input salah, dokumentasi, dan pemahamanmu juga dinilai.

Karena itu, jangan menghabiskan seluruh waktu demo hanya mengejar output visual. Sisakan ruang untuk menjelaskan satu-dua keputusan teknis.

Gunakan rubrik ini sebagai checklist persiapan, bukan sebagai alasan untuk menambah fitur di menit terakhir.

Setiap orang tetap harus mendapat kesempatan menunjukkan pemahaman

Lesson plan mengantisipasi durasi 60 menit. Jika jumlah siswa banyak, demo dapat dilakukan paralel dalam kelompok kecil atau peer panel, sementara guru berkeliling mengambil sampel penilaian langsung.

Reviewer tidak hanya menonton. Mereka perlu mengajukan pertanyaan atau memeriksa checklist agar aktivitas tetap aktif dan adil.

Jika kelas kecil, guru dapat memilih presentasi plenary satu per satu.

Project-mu adalah latihan nyata untuk konsep semester

Midtest mencakup Sesi 13–24. Saat membaca soal kode, jangan terburu-buru menebak. Trace nilai langkah demi langkah seperti saat kamu melakukan debugging.

Perhatikan kapan function dipanggil, kapan loop berhenti, kondisi mana yang benar, dan apa yang dicetak atau dikembalikan.

Selama assessment, bantuan guru hanya untuk masalah teknis akses, bukan jawaban soal. Pastikan jawaban benar-benar disubmit sebelum waktu selesai.

Presentasi selesai belum berarti submission selesai

Setelah demo dan Midtest, masih ada Checkout Quiz Sesi 24 serta pengumpulan artefak final. Pastikan tombol Submit/Kirim benar-benar ditekan.

Periksa link notebook dan slide dari perspektif reviewer: apakah file yang terbuka adalah versi terbaru dan apakah permission sesuai instruksi LMS/sekolah?

Jangan mengubah permission menjadi lebih terbuka dari yang diperlukan. Gunakan aturan berbagi yang sudah ditentukan kelas.

Refleksi membantu melihat perkembangan, bukan hanya hasil akhir

Pilih jawaban yang spesifik. “Coding susah” terlalu umum. Contoh yang lebih kuat: “Tantangan terbesar saya adalah menjaga List transaksi tidak ter-reset ketika kembali ke main menu.”

Untuk konsep yang paling dikuasai, berikan contoh dari project. Misalnya, kamu memahami while True karena menggunakannya untuk menjaga menu tetap berjalan sampai user memilih keluar.

Future improvement juga sebaiknya realistis, misalnya penyimpanan CSV/JSON sebelum berpikir ke GUI yang lebih besar.

Bukti terbaik adalah kombinasi “bisa jalan” dan “bisa dijelaskan”

Checklist ini merangkum target minimum Demo Day. Jangan hanya mengejar presentasi yang lancar jika kamu belum memahami kode, dan jangan hanya memahami kode tanpa menyiapkan alur komunikasi yang jelas.

Jika satu bagian belum sempurna, fokus pada bukti yang paling penting: fitur inti, error handling, state, dan penjelasan teknis yang jujur.

Kamu juga harus memastikan artefak sudah dikumpulkan dan aman dibagikan.

Satu project merangkum banyak kompetensi

Sepanjang sprint, kamu tidak hanya belajar syntax Python. Kamu belajar memecah masalah, menyimpan state, menangani human error, memvalidasi perhitungan, merapikan kode, menulis dokumentasi, dan menjelaskan produk.

Itulah alasan Demo Day menilai lebih dari tampilan output. Seorang developer perlu bisa menunjukkan bahwa solusi bekerja dan memahami mengapa solusi tersebut bekerja.

Gunakan pengalaman project ini sebagai fondasi untuk pengembangan berikutnya: penyimpanan permanen, visualisasi data, atau antarmuka yang lebih visual.

Penutup Sprint Project

Setelah presentasi, selesaikan evaluasi dan submission sesuai urutan kelas. Jangan meninggalkan link yang salah atau file yang belum bisa diakses reviewer.

Yang paling penting untuk dibawa ke semester berikutnya adalah kebiasaan kerja: bangun bertahap, uji, dokumentasikan, dan selalu pahami kode yang kamu gunakan.
